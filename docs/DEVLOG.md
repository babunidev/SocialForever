# SocialForever — development journal

**Human creative:** Babuni

## Retrospective reconstruction — 2026-10-26

SocialForever grew from a simple social problem: familiar people can remain strangely anonymous when playing with nameplates switched off. For me, the addon is meant to make recurring encounters easier to notice, target, invite and remember without turning the world into a permanent scanning overlay. The repository shows how that idea became a seven-module implementation covering proximity signals, encounter persistence, party ratings, sharing and list display.

Earlier release details are preserved in the changelog and development notes. This reconstruction does not pretend to recover conversations or decisions that were never recorded. AI contributed source review and documentation consolidation here, not the original idea and not an in-game test. Detection-source false positives, large-local-population behavior, invite prompts, group review, sharing privacy and SavedVariables migrations still required independent live verification at this point.

## 2026-10-27 — Audit #32: remembering people, not measuring them

Playing without nameplates can make the world feel anonymous even when the same people repeatedly share quests and roads. The direction behind SocialForever was to make those recurring encounters socially legible without replacing nameplates with another intrusive layer. For me, a familiar name should feel like somebody I have crossed paths with before, not like a reputation score generated by the addon.

Several revisions sharpened that idea rather than simply expanding the feature list. Version 0.3.0 divided the implementation into seven cooperating Lua modules. Version 0.3.1 protected selection through temporary list freezing and target priority. Version 0.4.1 split Nearby from Zone and added opt-in shared-mob grouping. Version 0.4.2 corrected misleading invited-state feedback. Version 0.4.4 kept personal flags private even when color marks were exchanged with peers. Version 0.4.5 introduced the small familiar-player thought, restrained by a persistent per-player cooldown. Version 0.4.6 removed empty tooltip clutter.

**Creative direction:** A more attentive, socially legible world rather than an intrusive scanning interface. **AI contribution in this audit:** Source-based consolidation and navigational documentation, not original authorship of the idea. **Verification:** README, TOC, selected modules, DEVELOPMENT and CHANGELOG were reviewed; the addon was not run, peer marks were not transmitted, real invites were not attempted and private player records were not accessed.

The release removes unattended invite paths, corrects Forever race/class icons, tightens raid Nearby behavior and refreshes sorting while keeping the remaining live checks explicit.

During release preparation, the first release-branch verification exposed a shell-quoting mistake in the new packaging assertion. That failure belonged to the CI harness rather than addon runtime behavior; the check was corrected and the release branch and final `main` verification both passed. AI handled the repository review, test automation, packaging checks and release preparation, while no live-client success was claimed.

## 2026-11-05 — Combat exposed a protected-row mistake

The first live launch-day error came from something the automated mocks had not reproduced: SocialForever was still resizing its secure player rows while the client was in combat lockdown. The invite and target macros were already guarded, but the row itself is a protected `SecureActionButtonTemplate`, so changing its height was enough for Forever to block the addon.

Rather than whack only the reported `SetHeight()` call and wait for the next protected layout call to fail, I kept the intended social detection running underneath and chose to freeze the secure list presentation during combat. AI traced the BugGrabber stack, identified the other row geometry and visibility mutations on the same path, implemented the deferred repaint, and added a regression test. Automated checks can prove that the mocked combat path no longer touches the secure rows; the real fix still needs to be reproduced in Forever before it is treated as live-verified.

## 2026-11-05 — A second protected call appeared

The first secure-row fix removed the blocked layout mutation, but live play immediately exposed another modern-client restriction: SocialForever still called `CheckInteractDistance` through a `pcall` while combat was active. The client blocks that action before Lua can treat it like an ordinary caught error, so wrapping it was never a real safety boundary.

For the hotfix, I kept the fallback deliberately conservative. SocialForever now skips `CheckInteractDistance` entirely during combat; exact distance still comes from `UnitDistanceSquared` when available, and loose visible-unit evidence can still keep appropriate tracked units in the list. AI traced the stack, added the hard combat guard and extended the regression test. The corrected path remains automated-tested until live combat confirms it.

## 2026-11-05 — Immediate 0.4.8-beta hotfix preparation

Two separate combat restrictions surfaced during live launch-day use: first the secure list rows were still being resized during combat, then `CheckInteractDistance` proved unsafe on SocialForever's combat path despite being wrapped in `pcall`. Because both failures affect ordinary play, I chose to package the corrections as a new beta immediately rather than touch the already published 0.4.7 tag.

Version 0.4.8-beta is deliberately narrow. Secure row presentation waits until combat ends, the protected interaction query is skipped during combat, and detection continues through the remaining safe evidence. AI prepared the fixes, regression coverage, version synchronization and release documentation. Automated verification is green; a successful live combat retest remains outstanding.

## 2026-11-05 — The focused combat retest stayed clean

After copying the exact 0.4.8-beta release candidate into the live Forever AddOns folder, I repeated combat with SocialForever active. The two BugGrabber failures that had driven the hotfix did not recur: no secure-row `SetHeight()` block and no protected interaction call appeared during the retest.

That is enough evidence for this narrow hotfix to move forward, but it is not a blanket verification of every SocialForever feature. AI updated the release record to preserve that distinction before publication.

## 2026-11-05 — Crafting is observable; Skinning is a different question

Standing beside another player made the gap obvious: fighting and then skinning a creature did not necessarily make that player appear in Nearby. The old implementation blurred several chat categories together and also kept a legacy three-second Combat Log parser that Forever's protected UI no longer allows to provide useful text.

The useful correction is narrower. Real craft announcements now enter through both the trade-skill and system-message routes, with Blizzard's own localized craft format used when text parsing is necessary. Skill-up messages are no longer treated as evidence of another player's crafting, and the dead Combat Log polling path is gone. Skinning remains deliberately unresolved: it is gathering, not crafting, and I do not want the addon inventing a nearby identity unless the live client actually exposes one.

## 2026-11-05 — Showing why somebody appeared

While checking crafting and combat detection, I wanted the list to explain itself rather than leave a name there without context. A person can now carry several observed reasons during the same Nearby appearance: perhaps I hovered them, then targeted them, then the Damage Meter showed that they were fighting beside me. The tooltip presents those as **Nearby because** while the older place memory stays under **Seen before in**.

That distinction matters. These labels describe what SocialForever actually observed in the current sighting; they are not permanent claims about what a player usually does. AI implemented the bounded provenance list, source labels, tooltip presentation and regression coverage.

## 2026-11-05 — The recognition thought must point to somebody visible

A familiar-player message occasionally arrived before the person appeared in Nearby. That made the little recognition thought feel detached from the actual world: it said I had seen this Paladin before, but the list gave me no immediate clue who it meant.

The rule is now simple: recognition is downstream of detection. A deliberate target is promoted through the ordinary Nearby path first, delayed recognition checks that the player is still present when its timer finishes, and combat-time recognition waits until the secure list can repaint after combat. The thought should only appear when SocialForever can also show the person it is talking about.
